# 武汉接线台多轮行程修复验收

部署版本为 `53f7efd`。公网业务验收使用独立测试会话，逐轮保存网页使用的 HTTP/SSE 接口响应，结束时删除测试会话。

## 游客可见的变化

- 游客说“今天不去”或“这趟都不去”时，接待员保存含适用范围的原话。续排时，模型根据原话选择仍然适用的限制编号，程序把它们绑定到新增日，并保留已经发给同行人的日卡。
- 地图创建的行程也可以试排。查看或采用备选时读取同一份已存版本，在中途问其他问题后仍可继续选择。选择原案会清除待采纳状态。
- 一组修改可为不同动作分别指定日期。模型负责判断时刻的用途，程序在提交前检查明确时刻是否已绑定到动作或被解释为对照。跨天挪站、放宽结束时间和调整出发时间在副本上统一计算，全部通过才保存。
- 同时排一日游、两日游并比较时，规划工具直接使用游客原话。该轮已经完整交付的方案可复用。服务返回本次 HTTP 请求实际发出的模型请求数，包含内部规划调用和重试。
- 限定交通方式时，排程与最终审核使用相同的交通约束。游客追问步行上限时读取已存的每段交通方式、步行米数和来源。缺米数或只有直线估算时，答复会说明证据不足。
- 九站等较长的固定路线可以重新排序。程序用已访问的站点集合及最后一站缩小候选，再逐段审核。时间不够时，若有经过复算的较晚结束时间，会把它作为待确认的选择。

## 为什么相同问法有时成功、有时失败

一类差异来自模型提取。例如同一句“这趟都不用安排”，曾被解释成仅限当时排出的日期。另一类来自前一天的实际交付。第二天有时较空，可以直接接收从第一天挪来的景点。有时第二天已经有八站，即使同样询问挪站，也需要另外留出游览和转场时间。

在保存的八站样本中，从汉口站出发，保留古琴台等八站并加入黎黄陂路，原定 18:00 结束。独立检查对每一对站点取可用时段内最短的转场，忽略开放时间和等候，枚举所有站点子集求最短总时长，得到乐观下界 18:06。排程器另找到了一条审核通过、18:08 结束的完整路线。18:00 约束下保留两天原卡，游客放宽时间后才允许提交。

另一个样本包括知音号、张之洞与武汉博物馆和汉阳造。加入黎黄陂路后一共七站，旧版按直线距离筛出的顺序全部超时。最终版本增加了基于实际转场的候选顺序。用原卡和原工具参数重放后，第1天改为 10:00 集合，第2天保留全部站点并在 17:49 结束。两份样本分别固定为可行和不可行回归。

## 版本与证据

完整公网轮次位于本机 `.local/visitor-repair/verified-9c376f5/`。14 条业务链、32 轮真实对话中，13 条直接通过。唯一失败是上述原本可行的七站路线。每轮模型请求中位数为 2.5，耗时中位数为 3.65 秒。一日游、两日游及比较的首次交付用了 8 次请求，调整两日游并更新比较用了 6 次。优化前曾观察到首次交付连续调用三次方案工具，共发出 28 次模型请求。这些数值来自单次完整批次。

隔离测试还曾发现时刻解析函数被同名局部变量遮蔽，导致编辑请求返回错误。该候选版本在发布前已纠正。一次 Windows 本地 HTTP 回归遇到连接中断，原用例单独重跑通过。

路线排序修复版 `899197a` 本地运行全部 147 项回归通过。通过公网重跑 7 条关键业务链、16 轮对话，7 条均通过，原始证据在 `.local/visitor-repair/production-899197a/`。新会话中的跨天路线实际排到 17:50，每轮模型请求中位数为 3，范围 2 至 9，端到端耗时中位数为 4.10 秒，最长 13.67 秒。此次首次生成两套方案及比较为 9 次调用、13.67 秒，随后局部修改并更新比较为 7 次、9.75 秒。

## 复核入口

- `python -X utf8 -m unittest discover -q` 会运行仓库回归，包括九站重新排序、复合修改回滚、版本过期、步行证据和作用域测试。
- `python -X utf8 audit/visitor_module_checks.py <新目录>` 离线检查知识检索与复合编辑。
- `python -X utf8 audit/visitor_acceptance.py --base https://saig.haiyuanwh.com --out <新目录>` 运行真实模型，会消耗额度。可用 `--cases` 选择业务链。随后执行 `python -X utf8 audit/grade_visitor_acceptance.py <同一目录>` 对原卡、预览卡、采纳结果和方案版本判分。
- `python -X utf8 audit/visitor_handoff_bound.py <同一目录>` 单独检验繁忙跨天案例的时间下界与两张原卡是否保留。这个复核保留原判分器的结果。
