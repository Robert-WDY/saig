# 武汉数命 SPU 城市 AI 接待员 · 参赛版验收规格

适用于中文手机网页、参赛简介和约两分钟的字幕演示。用例当前均为**待执行**。本规格验收四项功能、对话和路线的联动，以及评委能否亲自验证。官方分值为每项 25 分；下面的通过条件和发布门槛是项目内部建议。

## 1. 首版与理想体验的距离

| 部分 | 理想体验 | 首版能承诺什么 | 如何揭露差距 |
|---|---|---|---|
| 武汉介绍 | 理解游客所在区域，把历史、地理和兴趣连成可用的建议 | 用核实过的武汉资料回答，并能解释推荐与游客的关系 | W1 校事实，W2 用相同地点、相反兴趣做对照；分别记录准确性与有用性 |
| SPU 社区 | 说清到哪、谁能参加、怎样参与、今天有哪些活动 | 解释社区、地点、订单学习和已公布的信息 | C1 查实体混淆，C2 看访客能否找到下一步，C3 查未公布的到访条件 |
| SPU 与 SAIG | 解释概念，持续掌握最新公告，帮个人正确报名 | 区分个人能力、社区和赛事，依有日期的官方信息回答 | S1–S5 检验概念应用、提交清单、来源冲突、公告更新和赛制理解 |
| 路线覆盖 | 全市可靠路网，考虑开闭馆、换乘和游客体力 | 两条核验过的重点路线，半天/一天/两天；时长为估算 | R1–R8 检验可行性、地理与跨日、偏好、无解、边界、覆盖外请求和不确定耗时 |
| 连续接待 | 听得懂修正、指代和话题切换；解释改动并能从误解恢复 | 同一会话维护约束和原卡；含糊处追问一次 | D1–D6 按状态变化验，U1–U3 查实际显示、失败恢复与隔离 |
| 手机与角色 | 新游客无需指导即可使用，武汉话自然易懂 | 官方形象、三个入口、自由输入、简体文字、静音可用 | H1–H3 观察真实访客；选配 A1 独立验收语音 |
| 参赛交付 | 评委能看懂、复核、亲自尝试 | 公开体验链接、项目简介、完整字幕视频和赛事标签 | E1–E3 从评委设备、视频画面和报名材料分别核验 |

记录覆盖边界时分两栏写。例如成功说明“尚未核实此路段”可通过首版边界处理，但“此路段可精细排程”仍记为覆盖缺口。首版暂缺的全市路网、实时到访信息、英文、广覆盖语音不计入完成能力。

## 2. 准备答案和测试环境

1. **知识底稿。** 开测者从《武汉概览》《2026武汉旅游产品手册》、社区说明、SPU说明和赛事官网摘取要核查的事实，逐条记录文件页码或段落、页面地址、核对日期、允许的不确定表述。发布日期和运营状态单独记录。旧素材写有报名日期，现行官网曾标为待公告，两份都保留。录制当天重新取证，再冻结该轮底稿。[官方素材](https://shuming-official-file.markyin.com/static/file/SAIGS01CompetitionMaterials.zip) · [赛规](https://www.dlife.love/saig/#dday) · [报名表](https://www.dlife.love/saig/#register)
2. **路线底稿。** 测试者独立核对两条实地路线的站点、访问限制、起终点与跨江交通，建立有方向的转场耗时表。每个值标核对日期、估算区间和依据；不确定的时效信息明确列出。独立用纸笔或表格复算。开放式路线允许多种顺序，只核算约束、依据和游客偏好。
3. **证据。** 从手机页面走正常入口，保留输入、会话轮次、卡片前后截图、显示的资料来源。开发自测可额外抓取标准化约束、路线版本和时刻；内部值正确仍要通过页面验证。记录版本、设备、资料版本及运行模式。定时、来源冲突和依赖故障用可控夹具复现；公开链接、真实检索、实际模型和字幕在实际发布版本上另测。
4. **结果单。** 每族记录「ID｜版本与夹具｜输入/前置状态｜期待的约束｜实际原文或卡片｜证据位置｜通过/失败/阻塞/未测｜失败归因｜复测」。参数样本挂在原 ID 下。无法取得独立依据时标阻塞。

## 3. 结构化用例

一行是一类可以独立出现的缺陷。问句是可替换的例子。测试者可换说法；所有列出的必要观察都满足才通过。

### 官方四项功能

| ID | 主要缺陷 | 操作或输入 | 可观察的通过条件 |
|---|---|---|---|
| W1 | 城市事实或地理关系错误 | 首次问“武汉三镇怎么理解？我住江汉路，先从哪里认识武汉？” | 正确说出三镇，识别江汉路所在片区，至少解释一条与住处有关的地理关系；抽出的事实逐条对照底稿。 |
| W2 | 介绍真实但千人一面 | 同住江汉路的两人分别喜欢老建筑和江景，各问“为什么值得去？” | 两答各有一个有依据的观察点或活动，能解释与对应兴趣的关系。换掉称呼、保留同一段理由判失败；允许同一地点有两种有据的看法。 |
| C1 | 把社区、公司、比赛和个人混为一谈 | “智民里、数命科技、SPU、SAIG分别是什么关系？” | 准确区分场地、运营者、超级个体和赛事，说明社区如何把人和真实需求联系起来。对照社区说明。 |
| C2 | 能背社区简介，不能回答“我能做什么” | “我不会写代码，来社区能怎样学？能举个例子吗？” | 游客能复述从真实需求、带教或协作到交付的路径；例子如属假设须可辨认。回答能与普通旅游景点介绍区分。 |
| C3 | 把规划或未知信息说成今天可用 | 给出资料仅写“规划中”的体验项目，问“今晚能直接进吗？几点开？” | 区分规划和已确认开放，指出还需确认的具体信息与官方核对渠道；凭空给出开放时间或保证入场判失败。 |
| S1 | 记得 SPU 英文，却误解谁负责 | “我让 AI 一键出方案就算 SPU 吗？客户问交付有错，谁处理？” | 用人的判断、组织与交付责任解释这个例子，能用普通话说明 SPU 含义；只展开缩写不通过。 |
| S2 | 参赛建议导致漏交或错误承诺 | “我个人想参赛，只有简介和体验网址，下一步做什么？” | 指出缺完整可访问的演示视频，区分必交与选填，给官方入口；说明报名与入围的关系。按当天报名表核查。 |
| S3 | 多来源冲突时错用旧时间或混淆事件 | 同时提供素材包和 11 月 18 日官网快照，问“11 月 21 日还能报名吗？那时点赞还算吗？” | 在该历史快照下，分别说出报名截止待公告、点赞统计 11 月 20 日 23:59:59 北京时间截止；不能保证 21 日仍能报名。能指出这个结论依据哪份材料。 |
| S4 | 答案写死或缓存不更新 | 在测试环境把“截止待公告”替换为标明生效时间的新公告夹具，先问一次、更新资料，再开新会话问一次 | 新答采用新截止、标注新依据；点赞等未变字段保持不变。夹具明示为模拟，不向真实游客展示。发布前另与真实网页抽查。 |
| S5 | 混用线上评分、点赞和线下成绩 | “我的视频点赞少，四项功能都做好还有机会吗？现场成绩怎么算？” | 清楚区分线上四项各 25 分、人气直邀和赛区选拔两种入围路径、线下综合成绩的组成；人数和权重以冻结的官网底稿核算。游客能说清自己还有哪条路。 |
| R1 | 行程表看似合理，实际上少算一段时间 | 使用第 4 节固定夹具，保留 B、向车站倒排并回算每段 | 顺序、游览、逐段转场和进站余量均计入；数值能复算，估算在页面可见。 |
| R2 | 多日行程日期串位、跨江瞬移 | 两天分走汉口与武昌重点路线，指定首日收尾位置、次日出发地及返程站 | 每日从当日指定地点起算，跨江段若发生有方向和时间，次日计划落在正确日期。无需与参考路线逐站相同。 |
| R3 | 只认景点热度，软偏好无法改变选择 | 同一可行时间窗提供长步行和短步行两个真实可行选项，随后说“带妈妈，尽量少走路” | 步行负担可核实地下降，或给出两种有实质差异的选项；保留硬约束。时长和步行量单独判断。 |
| R4 | 无解时悄悄牺牲必去点或赶车余量 | 第 4 节用 13:30 开始，保留 B，15:00 发车；追问“两个都得满足” | 能指出同时满足的困难，保留原硬约束并给出需要游客同意的取舍；页面不会把冲突方案显示为已确认可行。 |
| R5 | 包含边界的判断写错 | 固定条件，连续运行最晚可出发时刻和晚一分钟两个样本 | 期望结果正好从可行翻为不可行。两次运行合计一个边界用例族。 |
| R6 | 输出超出已核验的路线覆盖 | “我想从一个未收录的小镇起步，按分钟排到智民里。” | 标出哪一段未核验，给出可继续的选择，如从已知接驳点起排。已知部分仍可用，未知段不生成精确承诺。 |
| R7 | 默认景点总能进入 | 在路线底稿中给一个点加入游览窗口，构造到达时已关闭、其余点仍可行的样本 | 识别窗口冲突并解释替代方案或调整访问顺序；避免把该点列为可入馆。开放窗口未核实应明示。 |
| R8 | 把交通估算的顺利情况当作保证 | 给回站路段设置 20–40 分钟区间，构造按 20 分刚好赶得上、按 40 分赶不上的行程 | 明示区间和赶车风险，采用保守时长重排或请游客取舍。单值夹具 R5 通过仍可能在此失败。 |

### 对话状态、界面和角色

| ID | 主要缺陷 | 操作或输入 | 可观察的通过条件 |
|---|---|---|---|
| D1 | 追问规则僵化 | 同一目标作一对冷启动：“帮我安排行程”；另一条含半天、住处和老建筑兴趣 | 首条只追问一个最有用的问题；第二条直接给初稿。答城市常识时也可直接回答。两条共测“何时需要信息”。 |
| D2 | 增量修正覆盖旧条件或黏住已撤销条件 | 已有两日卡，保留智民里；说“明早改十点，其余照旧”，随后“智民里这次不用去了” | 第一次仅变次日及受影响路段；第二次真正移除必去约束，首日、车次等继续有效。根据路线逻辑保留为可选点时须明确可跳过。 |
| D3 | 插入社区问答后丢失行程 | 先排路线，中途进入社区介绍，再说“回到刚才那张卡，给第二天少排一站” | 社区答复有独立内容；修改作用于原卡和正确日期，首日不被重生成。 |
| D4 | 模糊指代时擅自替用户选 | 原卡有两处老建筑，游客说“把那个老建筑删了” | 能指出两个可能对象并追问，确认前原卡保持有效；用户指明后准确删除。 |
| D5 | 把咨询误当作承诺修改 | 有一日卡，问“假如改成两天，能加什么？”接着说“先按原来的走” | 能解释备选；当前有效卡仍为一日，或清楚并列区分草案与已选行程。 |
| D6 | 一条话含两个任务时吞掉一个 | “我下午三点要到汉口站，顺便告诉我个人报名交什么。” | 卡片落实的是到站时间，答复同时覆盖报名材料；与“下午三点发车”的余量语义有清晰区别。 |
| U1 | 回复说已修改，实际卡片没改，或解释与变化不符 | 预设必须删一站才能保住 B 的场景，比较前后两张卡和解释 | 原会话呈现唯一可识别的最新版本；解释中的保留、删减、原因和卡片逐项对得上。可从同一对截图复核。 |
| U2 | 请求失败或重复发送造成半更新 | 编辑已有卡时让一次排程响应超时，再重试；故意连续点两次发送 | 等待/失败状态可见，旧有效卡可读；恢复后只有一次有效修改，输入无需重讲。分别保留故障和恢复画面。 |
| U3 | 两名游客的状态串用 | 两台手机或两个隔离会话分别住江汉路与武昌，交替触发路线更新 | 各自只看到自己的住处、路线和修改。另用无痕会话验证真正冷启动。 |
| H1 | 首页入口无法引导陌生人完成任务 | 先核对官方形象、三个开场问题逐个可用、自由输入框可见；再请至少两名没看过脚本的人独立用手机，一人从快捷问题进入，一人自由输入，主持人只给任务目标 | 两人均能无提示发起咨询、找到行程卡并自主追问。记录第一次卡住的位置、原因和是否求助；需主持人代点即失败。 |
| H2 | 手机布局遮住关键信息 | 窄屏真机打开键盘、滚到长行程底部、关闭键盘再修改 | 可以读到返程时间、剩余行程和来源，能发送下一问；按钮、字幕、气泡不遮挡关键内容。记录设备和截图。 |
| H3 | 武汉话抢过任务或让外地人误解 | 把“想晚起”的轻松场景和“会不会误车”的焦虑场景交给外地游客阅读，再由熟悉武汉话的人审阅语气 | 游客说得清下一步与时间；轻松场景台词自然，焦虑场景先给清晰处理方案。分别记录外地人理解和本地人语感。 |
| A1 | 可选音频破坏静音体验 | 仅在语音上线后测试：移动端点播、静音、模拟音频不可用 | 有字幕，语音与字幕含义一致且经听审；三种状态均能继续文字改线。语音未上线标“后置”，不阻塞主线。 |

### 评委看到的交付物

| ID | 主要缺陷 | 操作或输入 | 可观察的通过条件 |
|---|---|---|---|
| E1 | 开发机可用，评委链接打不开 | 在第二台手机用移动网络、无登录会话分别打开公开体验和演示视频；网页实际提问一次，视频拖动到结尾 | 两个地址均可访问，网页返回真实答复，视频可播放至末段。记录检查时间；发布平台若要求登录导致该环境无法观看，应修复或换可访问链接。 |
| E2 | 视频节奏流畅，四项输出实际看不清 | 让未看过脚本的人静音观看约两分钟成片，一遍后描述四项输出并指出路线如何变化 | 审阅者可指出四段实际输出及时间码，能读出至少一项保留或删减及其原因。产品界面要可辨认，只有标题、旁白或功能承诺不给该项通过。 |
| E3 | 体验正确，报名材料引用错链接或夸大能力 | 对照最终版简介、视频实际发布页和待提交表单预览，逐项检查必填字段和标签 | 简介提到的能力可在该版本验证，提交的是最终演示链接，视频使用平台对应的 SAIG 标签；若填写体验链接则打开对应版本。保存核对结果即可，无需实际提交报名。 |

## 4. 可手算的路线夹具

下列时长均是人为设定的测试数据。用于校验时间逻辑；真实路线另依第 2 节的武汉底稿验收。所有时刻指同一日当地时间。

| 输入 | 固定值 |
|---|---|
| 地点 | 起点 O；可选点 A；必去点 B；车站 T |
| 有方向的转场耗时 | O→A 10 分，A→B 20 分，O→B 20 分，B→T 30 分。只允许这些边。 |
| 游览与返程 | A 30 分，B 40 分；15:00 发车；进站余量 20 分；除列出时间外无其他等待。 |

- **12:30 出发。** O→A→B→T 用去 10+30+20+40+30＝130 分，14:40 到站，恰好满足进站余量；若明确要求“两站都去”，该方案可行。
- **13:00 出发。** 两站全去将于 15:10 到站；只保留 B 则于 14:30 到站，14:50 可完成进站。卡片应删 A、留 B，解释因为必须赶车。
- **13:10 / 13:11 出发。** 只走 B 分别于 14:40 / 14:41 到站。前者刚好可行，后者少 1 分。若漏算进站余量，后者会被错判为可行。
- **13:30 出发。** 仅保留 B 也要 15:00 才到站，加余量至 15:20。可建议更早出发、放弃 B 或更换车次，落实任何改变硬约束的方案须先获游客选择。

另一项独立对照：在相同路线中只把车站余量从 20 分提高到 30 分，可行解集合只能缩小或不变。这个检查复用 R1 数据，用于发现实现反向使用余量；不增加能力数。

## 5. 判分与放行

**四项能力各出一张成绩单。** 武汉介绍取 W1–W2，社区取 C1–C3，旅游规划取 R1–R8 并在 D2、U1 观察改线，SPU 与 SAIG 取 S1–S5。每项并列报告“事实或约束是否正确、是否对这个游客有用、静音视频中是否有可辨认的实际输出”，附失败 ID 和证据。官方每项上限 25 分；内部用通过、待修、未测表示，不预测导师分数。一次跨项演示只作端到端证据，不重复计算四次正确性测试。

**执行次序。** 首个原型先跑 R1、R4、R5、D2、U1，把可信的改线做出来。知识接入后再跑 W/C/S 和其余路线、对话族。录制前全跑主线，真实手机完成 H1–H3。发布后从评委视角跑 E1–E3。每个改动至少复测失败族、邻近约束和一条完整游客旅程；更换模型或路线数据后重跑相关组。建议对依赖生成的关键结论用三个干净会话复跑，报告逐次结果；任何一次关键事实或硬约束错误均需修复。重复运行只表示稳定性样本。

**发布判定。** 正式交付须让四项都有真实证据、所有首版用例有结论。错误赛务或地理事实、违反硬约束、展示与计算矛盾、两个游客串线、公开链接失效、视频缺任一评分项，均阻塞发布。其他失败记录对游客的具体影响，修复或明确列为已知限制再决定交付；不得将其写成通过。A1 后置。抽样通过只代表当前版本、设备和样本条件。

**盲测与参考上限。** 冻结用来调试的样本后，请一位未参与编写的人保留一条新任务到验收日，例如要少走路的同行者临时缩短停留时间，还插问一次赛事。让测试者自行措辞和决定优先级。由另一人用同份核验资料给出一个人工可行方案，再检查系统方案是否有遗漏、无谓折返、未满足偏好或需要额外操作。差距写成“多走哪一段 / 漏掉哪个前提 / 哪个决定游客做不了”；允许参考方案与系统路线都合格。总时长、等待时长、求助次数和失败原文照实记录，首次实测后再设性能阈值。

## 6. 防止同构用例膨胀

新增用例须写出**初始状态、触发操作、要保持或改变的约束、独立判据、相邻用例抓不到的错误**。如果只能改地名、时刻、表述或设备型号，挂成参数样本。只有条件跨越边界、导致新的决策分支或需要新的判据时才另列。半天/一天/两天、两条路线和不同手机要有抽样记录，但不用做成全排列。至少覆盖单日汉口、单日武昌、跨日两片区及半天紧时窗；每种支持时长和两条线都须实际跑到。

| 容易重复的做法 | 应保留的结构差异 | 可用来验证评测有效性的已知错误 |
|---|---|---|
| 换十个出发时间，都有充足余量 | 可删可选项、刚好可行、晚一分钟无解、硬约束相冲突 | 给评测者看漏扣进站时间的卡；R5 应指出 13:11 那条错在哪里 |
| 换十种说法问报名截止 | 旧文档与网页冲突、权威来源真的更新 | 让旧答永久缓存；S3 可能正确，S4 必须识别更新失败 |
| 换十个景点要求“保留它” | 局部修改、撤销要求、指代不清、假设性询问 | 将假设方案直接写入当前卡；简单改时间能过，D5 必须发现原卡被替换 |
| 把同一条录屏反复打勾 | 计算可行、界面忠实、独立用户能操作、外部评委能进入 | 让文字解释删除 A 但界面仍显示 A；路线算法可正确，U1 必须失败 |

执行前把上表的四个已知错误各做一份带错样例，盲交给测试者；记录其能否指出出错位置和违反的约束。漏检时先补判据，再增加用例。模型可以辅助提取待核的声明；事实、时间算术、界面可用性与方言语感各由相应的独立证据裁决。
